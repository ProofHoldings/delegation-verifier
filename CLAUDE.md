# Delegation Verifier CLAUDE.md

## Purpose

`@proof-holdings/delegation-verifier` — the issuer-agnostic reference verifier for Proof of Delegation (`m-delegation-verifier-ref`). A **non-customer** (a gateway, a registry, an agent runtime) runs this to check that the domain in `principal` authorized the artifact in `delegate`. Zero runtime dependencies; ESM-only; Node ≥18 or any runtime with WebCrypto + `fetch` + `DecompressionStream`.

## Narrative Summary

This is deliberately **not** an SDK. The four SDKs in `sdks/` are clients for calling OUR API: they carry auth, an HTTP stack, and they pin proof.holdings as the issuer. A gateway verifying a delegation is not our customer — it wants a small dependency that verifies **anyone's** delegation, ours included. Two rules follow, and both are load-bearing:

- **No default trust list.** `trustedIssuers` is a required argument on every call; an empty list fails closed with `no_trust_policy`. A verifier that trusts an issuer because the library shipped with its name compiled in is a client for that issuer. (PHP's unpinned `JWT::decode` is the WRONG shape, not an early version of this one: issuer-agnostic means a caller-supplied trust policy, not the absence of one.)
- **`delegate` is required.** A published token is a bearer artifact — anyone can copy a genuine one into their own card. The comparison against an identity the CALLER resolved independently is what defeats that, so omitting it is `invalid_options`, never a silently skipped check.
- **`expectedPrincipal` closes the other half, and the result says whether it was asked.** An issuer binds `delegate` to NOTHING (`src/controllers/delegations.ts` canonicalizes free-text from the requester and derives `principal` from whatever domain they proved), so any domain owner can mint a valid delegation naming someone else's package. `delegate` stops a COPIED token; only pinning `principal` stops one MINTED by the wrong party. The option stays optional because a directory legitimately asks "who claims this artifact?", but the success result carries `principalChecked` and the MCP tool makes the pin mandatory — an agent installing a package always knows whose package it thinks it is.

Verification order is chosen so every network-free rejection happens first: trust policy → algorithm → claims → principal → delegate → (only then) signature → status. A token from an untrusted issuer, about someone else's artifact, or expired costs zero outbound requests — measured per verdict on live tokens in `docs/delegation-e2e-walkthrough.md` § 8 (0 for `delegate_mismatch`/`principal_mismatch`/`expired`; a `revoked` or a genuine acceptance now both cost 2 — jwks + status list — since `h-delegation-verifier-status-fallthrough-gate` stopped double-checking a `valid`/`revoked`/`suspended` list bit against the endpoint; the walkthrough's own numbers predate that change and want re-measuring).

The order has a consequence callers get wrong: **a `reason` reports where the walk stopped, not what the later checks would have said.** `expired` is decided before both pins, so a genuinely expired delegation and an expired token copied into a stranger's card are indistinguishable by reason alone; only `valid: true` means every check ran. Stated in the README's failure-reason section and pinned by `verify.test.ts` → "reports expired even when the principal and delegate pins would also have failed", which carries a positive control so it cannot pass vacuously if the fixture's defaults drift.

## Key Files

- `src/verify.ts` — `verifyDelegation(token, options)`, the chain above. Returns a discriminated `VerificationResult`; failures carry a machine-readable `reason` (see the README table).
- `src/types.ts` — the public contract (`TrustedIssuer`, `VerifyOptions`, `FailureReason`, …) plus the rationale for the two rules.
- `src/jwks.ts` — key fetch + cache. The algorithm comes from `SUPPORTED_ALGORITHMS` (RS256/ES256), NEVER from the token header, so `alg: none` and HMAC forgeries die before a key lookup. An unknown `kid` triggers at most one refetch per `KEY_MISS_COOLDOWN_MS` (30s) and concurrent misses share one in-flight fetch — the same reasoning as the Go SDK's hand-rolled verifier: without both, every junk-kid token costs an outbound request and a busy verifier trips the issuer's own rate limit, failing its GOOD tokens too.
- `src/status.ts` — the two revocation channels and why both are still needed once the list is authoritative. `checkDelegationStatus` (`h-delegation-verifier-status-fallthrough-gate`) trusts a `valid`/`revoked`/`suspended` list read outright and does NOT also ask the issuer's endpoint — since `h-status-list-cascade-fold` the list packs the domain control-proof cascade straight into the bit (see `src/services/statusList.ts`'s `packDelegationAwareValue`), so a set/unset bit is the issuer's whole answer for revoked/suspended. The endpoint still fires on `unavailable`/`untrusted_uri` (the list could not be read, not an answer from it) and stays the ONLY channel for `unknown_delegation`, a token with no status-list claim at all, and cascade-derived **expiry** — never packed into the bit by design, bounded but not eliminated by `h-fix-control-proof-reissue-shorter` (see that file's own header comment and the README for the exact residual). `valid: false` from the endpoint is NOT automatically "withdrawn" either way: only `revoked`/`suspended`/`expired`/`unknown_delegation` map to a verdict, anything else (including proof.holdings' own `status_unavailable` on a registry read failure) fails closed as unavailable. The status-list uri arrives INSIDE the artifact being verified, so it is refused unless its origin belongs to the trusted issuer (falling through to the real, caller-configured endpoint rather than being fetched), and the list's own signature is checked against the same key set. Every `VerificationFailure` also carries `outcome: 'invalid' | 'unconfirmed'` via the exported `classifyFailureReason` — `unconfirmed` for the three reasons that mean the check itself could not run (`status_unavailable`, `jwks_unavailable`, `status_uri_untrusted`), `invalid` for a completed check with a negative verdict.
- `src/carriers.ts` — where a delegation may be published. FOUR carriers, and the fourth is shaped unlike the others: three are LOCATIONS INSIDE A CARD holding the publication itself (MCP `_meta`, registry publisher-provided nesting, A2A `capabilities.extensions[]`), while `parseDelegationPointer` reads a `_mcp.<domain>` TXT record that holds no publication at all — it holds the ADDRESS of a card that does (`m-delegation-dns-publish`; format in `docs/delegation-dns-pointer.md`). The first three are read from an artifact one already has; the pointer is read from a DOMAIN and leads to the card, which is the only route open to an owner who cannot write `.well-known`. Only the PARSE half is here — resolving a pointer means a DNS query and a card fetch, and this package takes no dependencies, so a consumer does the lookup with its own resolver and hands the TXT values in. Crypto-free on purpose. Refusals are a closed vocabulary and carry no free text (`no_pointer`, `version_not_first`, `missing_card`, `duplicate_field`, `invalid_card_url`, `ambiguous_pointer`, `token_in_dns`) precisely because two copies must agree byte for byte. Two rules worth knowing before changing it: a record whose first field is not `v=proofdlg1` is somebody else's (the MCP discovery draft uses the same name with `v=mcp1`) and is skipped silently, while a record of OURS that is malformed is a refusal even when a well-formed sibling exists — a zone in an unknown state is not a zone to guess about.
- `src/publication.ts` — `verifyPublishedDelegation(card, options)`; refuses to guess when a card publishes two DIFFERENT tokens.
- `src/delegate.ts`, `src/jwt.ts` — canonicalization and an unverified structural JWT parse (an empty signature segment is parsed, not rejected, so the algorithm gate gives the useful answer instead of `malformed_token`).

## ⚠️ Lockstep copies — two files, three pieces of issuer-side code

`src/delegate.ts` and `src/carriers.ts` are COPIES of issuer-side code: `src/utils/delegateIdentifier.ts`, the extraction half of `scripts/delegation-publication-shared.ts`, and — since `m-delegation-dns-publish` — the pointer parser in `src/services/delegationPointer/pointer.ts`. They are copied rather than imported because the package must not drag the backend into a gateway's dependency tree. (The pointer parser lives in `src/services/` rather than beside the other carrier code because `web/__tests__/mcp-servers-positioning.test.ts` imports that module, and a re-export there would pull backend `src/` into the web test graph.)

All three are pinned by `src/__tests__/drift/delegation-verifier.test.ts` in the repository root, which runs ONE shared vector through BOTH implementations and requires identical behaviour — including identical rejections. Divergence in canonicalization turns a valid delegation into `delegate_mismatch`; divergence in carriers makes a real delegation invisible. Change one side, change the other, and let the drift suite prove it.

A third copy of the carrier bindings exists in the issuer repository (`src/services/lookalikeWatch/carriers.ts`, pinned by its own drift suite) and deliberately does NOT carry the pointer: that sweep is entered from an artifact, which has no domain to query, and already fetches the artifact's card directly. The exclusion is written into that file's header and pinned as an absence, so it stays distinguishable from an oversight.

## Build/Test

- `npm run build` / `npm test` (vitest, `src/__tests__/`), or from the repository root: `npm run verifier:build` / `npm run verifier:test`.
- Tests use real WebCrypto keys and real signatures with a routed mock `fetch` that COUNTS requests — several cases assert that a rejection cost zero outbound calls, which only a counting fetch can prove.

## Consumers

- `mcp/src/tools/delegation-verify.ts` — the `verify_delegation` MCP tool (one artifact, threads the package's `outcome` straight into its JSON response) and `verify_delegations` (up to 50, `h-proof-checker-mcp`), both needing no API key. The batch tool's outcome map (`delegation-verify-outcomes.ts`) is a LOCAL 3-bucket classification (`confirmed_invalid`/`no_claim_found`/`unconfirmed`), scoped to the MCP tool — it now DERIVES from this package's binary `classifyFailureReason` for every reason except four explicit overrides (`no_publication`, `multiple_publications`, `invalid_options`, `no_trust_policy`) where the local vocabulary reads differently than the binary split would by default; see the file's own comment for why those four stay hand-mapped. Until the package is published, `npm run verifier:link` (repo root) links it into `mcp/node_modules`; `mcp/vitest.config.ts` aliases the source so the MCP suite is green on a fresh clone.
